# RAG Memory με Standardised SQL — Πτυχιακή Εργασία

Πειραματική επέκταση του [Xander](https://github.com/henrijsprincis/Xander) — από το paper "Enhancing SQL Query Generation with Neurosymbolic Reasoning" — με έναν εξωτερικό μηχανισμό μνήμης τύπου Retrieval-Augmented Generation (RAG): αντί το μοντέλο να στηρίζεται μόνο στη δική του γνώση, πριν απαντήσει ανακτά παλιά παραδείγματα (ερώτηση, SQL) και τα βάζει στο prompt ως οδηγό.

Η εργασία ξεκίνησε ρωτώντας αν η μορφή αποθήκευσης αυτών των παραδειγμάτων έχει σημασία. Κατέληξε να απαντάει σε ένα δεύτερο ερώτημα, που προέκυψε από τα ίδια τα αποτελέσματα: **γιατί μια μετρήσιμη βελτίωση στο retrieval δεν παράγει καλύτερες απαντήσεις.**

## Με μια ματιά

| Ερώτημα | Απάντηση |
|---|---|
| Βοηθάει η Standardised SQL το retrieval; | **Ναι.** 19.0% → 20.4% top-1 (p = 0.04), επιβεβαιωμένο σε δεύτερο embedding model |
| Μεταφέρεται στο execution accuracy; | **Όχι.** 733 → 732 από 1034 (p = 1.0000) |
| Γιατί όχι; | Υπάρχουν **μόνο 3.97 μονάδες** περιθώριο συνολικά, και το πείραμα μπορούσε να δει διαφορές από ~3 μονάδες και πάνω |
| Πόσο πιάνει το schema linking; | **+0.58 από τις 3.97**, με το μισό context — ισοδυναμία, όχι βελτίωση |
| Τι απομένει; | **16.5%** των ερωτήσεων αποτυγχάνει κάτω από κάθε συνθήκη που δοκιμάστηκε |

Αναλυτικά, με πλήρη τεκμηρίωση: `technical_document_v2.docx` σε αυτό το repository.

## Ερευνητικό ερώτημα

Το Xander εισάγει τη **Standardised SQL**, μια τυποποιημένη μορφή SQL (κεφαλαία keywords, υποχρεωτικά clauses ακόμα κι όταν είναι κενά, επέκταση aliases σε πλήρη ονόματα), με στόχο τη μείωση θορύβου κατά το fine-tuning ενός μικρού μοντέλου.

Το αρχικό ερώτημα: εμφανίζεται το ίδιο όφελος σε διαφορετικό πλαίσιο — στο **retrieval quality** μέσα σε ένα σύστημα RAG, και τελικά στο **execution accuracy**;

Και τα δύο σκέλη απαντήθηκαν νωρίς: ναι για το retrieval, όχι για την ακρίβεια. Όλες οι επόμενες δοκιμές υπηρετούν το ερώτημα που γεννούν αυτές οι δύο απαντήσεις μαζί.

**Κριτήριο επιτυχίας:** κάθε ισχυρισμός ποσοτικοποιημένος με δηλωμένη αβεβαιότητα, και κάθε αρνητικό αποτέλεσμα να συνοδεύεται από μέτρηση του τι θα μπορούσε να είχε ανιχνευθεί. Ένα «δεν βρήκαμε διαφορά» δεν στέκει μόνο του. Στέκει όταν γίνεται «αποκλείουμε διαφορά μεγαλύτερη από Χ».

## Μεθοδολογία

1. Δύο vector databases πάνω στο [Spider dataset](https://yale-lily.github.io/spider) (7000 training παραδείγματα, 140 databases): **Memory A** (raw SQL), **Memory B** (Standardised SQL). Σε ένα vector database κάθε παράδειγμα αποθηκεύεται ως embedding, ώστε να βρίσκουμε γρήγορα παραδείγματα με παρόμοιο νόημα.
2. **Asymmetric semantic search**: το κείμενο στο index (Question + Schema + SQL) περιέχει περισσότερη πληροφορία από το κείμενο αναζήτησης (Question + Schema μόνο — το SQL δεν είναι ακόμα γνωστό).
3. Ανάκτηση **top-k = 3** παραδειγμάτων ανά dev ερώτηση, από κάθε μνήμη ξεχωριστά.
4. Παραγωγή SQL μέσω **gpt-4o-mini**, με τα ανακτημένα παραδείγματα ως few-shot prompt.
5. **Execution accuracy**: εκτέλεση του παραγόμενου SQL στην πραγματική SQLite βάση και σύγκριση με το gold αποτέλεσμα.
6. **Retrieval quality** (SQL skeleton matching): το skeleton είναι η δομή ενός ερωτήματος χωρίς τις συγκεκριμένες τιμές. Μετράμε αν τα ανακτημένα παραδείγματα έχουν το ίδιο skeleton με το gold query, πριν καν μπει το LLM στην εικόνα.

Ο νευροσυμβολικός πυρήνας του Xander (Best-First Search, Partial-Query Checker, Query Test-and-Repair) **δεν** ενεργοποιείται: λειτουργεί πάνω σε token-level πρόσβαση ενός τοπικά fine-tuned μοντέλου, ασύμβατο με API μοντέλο.

**Στατιστική.** Όλες οι συγκρίσεις είναι ζευγαρωτές (paired): οι ίδιες 1034 ερωτήσεις κάτω από δύο συνθήκες, οπότε πληροφορία φέρνουν μόνο οι ερωτήσεις που άλλαξαν απάντηση. Χρησιμοποιείται ο ακριβής έλεγχος **McNemar**, και κάθε σύγκριση συνοδεύεται από **confidence interval** 95% και από το κατώφλι ανίχνευσης (**minimum detectable effect**) — δηλαδή πόσο μεγάλη έπρεπε να είναι μια διαφορά για να μπορέσει καν να φανεί. Πλήρης εξήγηση με παράδειγμα στο §2.4 του technical document.

## Αποτελέσματα

### 1. Πλήρες dev set (1034 ερωτήσεις, 20 βάσεις)

Ένα αρχικό pilot σε μία βάση (concert_singer, 45 ερωτήσεις) έδειχνε τη Memory B μπροστά (40/45 έναντι 37/45). Το εύρημα **δεν γενικεύτηκε**:

| Συνθήκη | Execution Accuracy |
|---|---|
| Baseline | 737/1034 (71.3%) |
| Memory A (raw SQL) | 731/1034 (70.7%) |
| Memory B (Standardised SQL) | 733/1034 (70.9%) |

McNemar Baseline έναντι B: p = 0.7807. A έναντι B: p = 0.9261.

### 2. Η διόρθωση boilerplate — το θετικό εύρημα

Η Standardised SQL γράφει ρητά κάθε clause ακόμα κι όταν είναι κενό (ένα απλό SELECT γίνεται `... GROUP BY NONE ORDER BY NONE HAVING NONE ...`). Στο embedding, οι επαναλαμβανόμενες λέξεις "NONE" παίρνουν δυσανάλογο βάρος και **αραιώνουν** το πραγματικό περιεχόμενο του ερωτήματος.

Η διόρθωση: αφαίρεση των κενών clauses **μόνο** από το κείμενο που γίνεται embed. Η πλήρης Standardised SQL, με όλα τα NONE, παραμένει αυτή που βλέπει το LLM στο few-shot prompt. Δεν αλλάζει τι μαθαίνει το μοντέλο, μόνο πώς βρίσκουμε ποια παραδείγματα να του δείξουμε.

| Μνήμη | Top-1 (πριν) | Top-1 (μετά) | Top-3 (πριν) | Top-3 (μετά) |
|---|---|---|---|---|
| Memory A (αμετάβλητη) | 20.8% | 20.8% | 32.0% | 32.0% |
| Memory B (compact) | 19.0% | **20.4%** | 31.2% | **32.5%** |

McNemar (Memory B πριν έναντι μετά): **p = 0.0400**. Επαναλήφθηκε με δεύτερο embedding model (all-mpnet-base-v2): 30.7% → 32.9% top-1, **p = 0.0469**.

Στο execution accuracy όμως: 733 → 732, p = 1.0000. **Εδώ γεννιέται το κεντρικό ερώτημα της εργασίας.**

### 3. Schema linking: πόσο περιθώριο υπάρχει συνολικά

Πρώτη υπόθεση: μήπως το prompt πνίγεται σε άσχετη πληροφορία; Μέχρι εδώ το LLM έβλεπε πάντα **ολόκληρο** το schema της βάσης, ακόμα κι όταν η ερώτηση χρειαζόταν 2-3 στήλες.

Για να το ελέγξω χρειαζόμουν μηχανισμό που ανακτά μόνο το σχετικό κομμάτι του schema. Υλοποίησα πιστά τον μηχανισμό του ["Rethinking Schema Linking: A Context-Aware Bidirectional Retrieval Approach for Text-to-SQL"](https://arxiv.org/abs/2510.14296): τέσσερις κλήσεις LLM ανά ερώτηση — εξαγωγή keywords, διάσπαση σε υπο-ερωτήσεις, **Table-First** retrieval (ολόκληροι πίνακες), **Column-First** retrieval (μεμονωμένες στήλες), και ένωση των δύο.

Πριν από αυτόν δοκιμάστηκαν δύο φθηνότερες εκδοχές χωρίς κλήσεις LLM, βασισμένες μόνο σε ομοιότητα embeddings: 677/1034 (65.5%) και 688/1034 (66.5%), και οι δύο **χειρότερες** από το πλήρες schema με p < 0.000001. Το schema linking απαιτεί σημασιολογική κατανόηση, όχι απλή ομοιότητα κειμένου.

Επιπλέον υπολογίζεται ένα **Perfect (oracle) schema** — οι ακριβείς πίνακες και στήλες που χρειάζεται το gold SQL, εξαγόμενοι με `sqlglot`. Δεν είναι ρεαλιστική μέθοδος, είναι το **θεωρητικό ταβάνι**.

| Επίπεδο | Recall (SLR) | False positives (FPR) | Μέση διατήρηση |
|---|---|---|---|
| Πίνακες | 98.79% | 9.09% | 45.89% |
| Στήλες | 98.62% | 37.69% | 49.83% |

| Συνθήκη | Execution Accuracy | Διαφορά | 95% CI | McNemar |
|---|---|---|---|---|
| Full (πλήρες schema) | 737/1034 (71.3%) | — | — | — |
| Retrieved (ο μηχανισμός) | 743/1034 (71.9%) | +0.58 | [−0.70, +1.87] | p = 0.4614 |
| Perfect (oracle) | 778/1034 (75.2%) | **+3.97** | [+1.93, +6.00] | **p = 0.0002** |

**Το +3.97 είναι όλο το περιθώριο** που υπάρχει σε αυτό το πρόβλημα για οποιαδήποτε παρέμβαση στην πλευρά του retrieval. Ο πραγματικός μηχανισμός πιάνει το 15% του και είναι στατιστικά **ισοδύναμος** με το πλήρες schema — ίδια ακρίβεια με το μισό context.

**Πού χάνεται η απόσταση.** Το Perfect βγάζει 778 και το Retrieved 743, διαφορά 35 ερωτήσεις. Χωρίζοντας τις ερωτήσεις ανάλογα με το αν ο μηχανισμός έχασε κάτι αναγκαίο (κριτήριο που δεν κοιτάζει καθόλου αν η απάντηση βγήκε σωστή):

| Ομάδα | Ερωτήσεις | Retrieved | Perfect | Κενό |
|---|---|---|---|---|
| Πετάχτηκε κάτι αναγκαίο | 22 | 22.7% | 40.9% | 4 |
| Δεν πετάχτηκε τίποτα | 1012 | 72.9% | 76.0% | 31 |

Τα δύο κενά αθροίζουν στις 35. Άρα **31 από τις 35, το 89%**, έρχονται από ερωτήσεις όπου δεν χάθηκε τίποτα (p = 0.0017). Είναι πρόβλημα **ακρίβειας**, όχι recall: δίνονται 11.1 στήλες εκεί που χρειάζονται 2.7.

**Γιατί.** Το `22_worked_example.py` τρέχει τον μηχανισμό σε μία ερώτηση και δείχνει κάθε ενδιάμεσο βήμα. Για την ερώτηση *«Show the stadium name and the number of concerts in each stadium»*, και το Table-First και το Column-First εντόπισαν **ακριβώς τις τρεις σωστές στήλες**, ταυτόσημες με το oracle. Το schema που μπήκε στο prompt είχε όμως **δώδεκα**. Αιτία ο κανόνας της ένωσης: κάθε πίνακας που επιλέγει το Table-First μπαίνει με ολόκληρο το περιεχόμενό του, όπως ορίζει το prompt του paper. Η υπερβολή είναι σχεδιαστική επιλογή, όχι σφάλμα — και εδώ μετρήθηκε το τίμημά της.

### 4. Οι δύο μηχανισμοί μαζί

Η υπόθεση ήταν ότι ο θόρυβος του schema πνίγει τα few-shot παραδείγματα. Μέχρι εδώ όμως οι δύο μηχανισμοί είχαν δοκιμαστεί μόνο χωριστά, οπότε δύο συνδυασμοί δεν είχαν τρέξει ποτέ. Τους συμπλήρωσα με 2 × 1034 νέες κλήσεις:

| | Χωρίς παραδείγματα | Raw (A) | Standardised (B) |
|---|---|---|---|
| **Full schema** | 737 (71.3%) | 731 (70.7%) | 732 (70.8%) |
| **Retrieved schema** | 743 (71.9%) | 737 (71.3%) | 739 (71.5%) |

**Cochran's Q = 2.206, p = 0.8199** — καμία από τις έξι συνθήκες δεν διαφοροποιείται. Ο interaction test δίνει **+0.00** (p = 1.0000) για τα raw και **+0.10** (p = 1.0000) για τα τυποποιημένα.

Οι δύο μηχανισμοί είναι **ορθογώνιοι**. Φαίνεται και στο πλέγμα: το schema linking δίνει σταθερά `743−737 = +6`, `737−731 = +6`, `739−732 = +7` ερωτήσεις, ό,τι κι αν συμβαίνει με τα παραδείγματα.

### 5. Τι είναι τα λάθη που μένουν

Από τις 1034 ερωτήσεις, οι **863 (83.5%)** απαντώνται σωστά κάτω από τουλάχιστον μία από τις έξι συνθήκες, ενώ οι **171 (16.5%)** αποτυγχάνουν κάτω από όλες — εμπειρικό άνω φράγμα για ό,τι δοκιμάστηκε.

| Συνθήκη | Διορθώνει | Χαλάει | Καθαρό |
|---|---|---|---|
| Memory A | 55 | 61 | −6 |
| Memory B (compact) | 50 | 55 | −5 |
| Schema linking | 26 | 20 | +6 |
| Perfect schema | 79 | 38 | +41 |

Οι μηχανισμοί μνήμης **δεν είναι αδρανείς**: διορθώνουν 50-55 ερωτήσεις από τις 297 που χάνει το Baseline, αλλά χαλάνε 55-61 από τις 737 που βρίσκει. Το μηδενικό αποτέλεσμα είναι αλληλοαναίρεση, όχι αδράνεια.

| Τύπος αποτυχίας | n | Μερίδιο | Memory B | Schema link | Perfect |
|---|---|---|---|---|---|
| Λάθος περιεχόμενο | 139 | 46.8% | 15.1% | 7.9% | 23.7% |
| Λάθος πλήθος στηλών | 46 | 15.5% | 21.7% | 15.2% | 37.0% |
| Κενό αποτέλεσμα | 45 | 15.2% | 11.1% | 6.7% | 31.1% |
| Υπερβολικά ανεκτικό | 31 | 10.4% | 22.6% | 0.0% | 12.9% |
| Υπερβολικά περιοριστικό | 14 | 4.7% | 7.1% | 0.0% | 28.6% |
| **Ανύπαρκτη στήλη ή πίνακας** | **12** | **4.0%** | 41.7% | **41.7%** | 58.3% |
| Λοιπά | 10 | 3.4% | — | — | — |

Η τελευταία γραμμή εξηγεί το συνολικό αποτέλεσμα. Είναι ακριβώς το πρόβλημα που στοχεύει το schema linking, και εκεί ο μηχανισμός διορθώνει το 41.7% — μακράν το καλύτερό του. Αλλά η κατηγορία είναι 12 ερωτήσεις από τις 297, και το 41.7% από αυτές είναι **5 ερωτήσεις**. Αυτό είναι όλο το όφελος που μπορεί να αποδώσει εκεί που στοχεύει.

### 6. Δύο δοκιμές που δεν απέδωσαν

**Value grounding.** Μηχανισμός που ψάχνει την πραγματική τιμή μέσα στη βάση όταν το SQL είναι δομικά σωστό αλλά η τιμή δεν ταιριάζει (`'Europe'` ενώ η βάση έχει `'europe'`).

| Συνθήκη | Πριν | Μετά | Διόρθωσε | Χάλασε | p |
|---|---|---|---|---|---|
| Baseline | 737 | 736 | 18 | 19 | 1.0000 |
| Memory A | 731 | 725 | 14 | 20 | 0.3915 |
| Memory B (compact) | 732 | 733 | 10 | 9 | 1.0000 |

Ίδιο μοτίβο με τους μηχανισμούς μνήμης: διορθώνει και χαλάει ισάριθμες. Επιπλέον άλλαξε μόλις 61/1034 queries (5.9%) — μόλις που ενεργοποιήθηκε. Η ταξινομία σφαλμάτων δείχνει ανεξάρτητα ότι η κατηγορία που στόχευε είναι η μεγαλύτερη (46.8%): η παρέμβαση ήταν σωστά στοχευμένη και παρ' όλα αυτά δεν απέδωσε.

**Merit metric.** Απλοποιημένη εκδοχή του Merit από το ["Retrieval-Augmented NL2SQL Generation with Data-Centric Query Capsules"](https://dl.acm.org/doi/10.1145/3767695.3769489): structural score μέσω tree edit distance (`sqlglot` + `zss`) και semantic score μέσω cosine similarity, σε ένα F1. Merit A = +0.0189, Merit B (πριν) = −0.0169, Merit B (μετά) = −0.0184 — δεν στηρίζει την υπόθεση.

## Ερμηνεία

Τρία νούμερα συνοψίζουν τα ευρήματα:

- Όλο το περιθώριο για οποιαδήποτε παρέμβαση στο retrieval είναι **3.97 μονάδες**.
- Το πείραμα μπορούσε να δει διαφορές από **~3 μονάδες** και πάνω (minimum detectable effect: 2.73 έως 3.07 στις συγκρίσεις μνήμης).
- Το **16.5%** των ερωτήσεων αποτυγχάνει κάτω από κάθε συνθήκη.

Ο χώρος μέσα στον οποίο ένα θετικό αποτέλεσμα θα ήταν ταυτόχρονα υπαρκτό και ορατό είναι επομένως πολύ στενός, και αυτό εξηγεί τα περισσότερα αρνητικά αποτελέσματα. Η ταξινομία σφαλμάτων εξηγεί γιατί το περιθώριο είναι τόσο μικρό: μόλις το 4% των αποτυχιών είναι του είδους που πιάνει ένας μηχανισμός retrieval.

Υπάρχει και ένας δομικός περιορισμός. Στο Spider τα databases του training και του dev δεν επικαλύπτονται, οπότε τα ανακτημένα παραδείγματα έρχονται πάντα από ξένη βάση με διαφορετικό schema. Μπορούν να μεταφέρουν μόνο δομή ερωτήματος, ποτέ γνώση για τη συγκεκριμένη βάση.

**Δύο συνεισφορές.** Η πρώτη: η Normalized SQL του Xander σχεδιάστηκε αποκλειστικά για fine-tuning, ποτέ για embedding-based retrieval. Εντοπίστηκε ότι το χαρακτηριστικό που την κάνει χρήσιμη στο πρώτο γίνεται πρόβλημα στο δεύτερο, προσαρμόστηκε, και αποδείχθηκε στατιστική βελτίωση σε δύο ανεξάρτητα embedding models. Η δεύτερη, διαφορετικού τύπου: η ποσοτική οριοθέτηση του τι μπορεί και τι δεν μπορεί να πετύχει ένας μηχανισμός retrieval εδώ, με μετρημένο ταβάνι, δηλωμένη στατιστική ισχύ, και ταξινόμηση των σφαλμάτων που μένουν εκτός εμβέλειας.

## Περιορισμοί

- **Ένα βασικό μοντέλο** (gpt-4o-mini). Ένα ασθενέστερο μοντέλο θα άφηνε μεγαλύτερο περιθώριο στο retrieval.
- **Ένα dataset.** Το Spider έχει απλά schemas και το μοντέλο πιάνει ήδη 71.3% χωρίς βοήθεια. Το ίδιο το paper του schema linking αναφέρει τα μικρότερα κέρδη του ακριβώς στο Spider και μεγαλύτερα σε benchmarks όπως το BIRD.
- **Μία εκτέλεση ανά συνθήκη.** Η διακύμανση μεταξύ επαναλήψεων δεν μετρήθηκε.
- **Μία μετρική ορθότητας.** Το execution accuracy μπορεί να περάσει λανθασμένο query κατά σύμπτωση. Τέσσερα gold queries του dev set δεν εκτελούνται καθόλου και διατηρήθηκαν για συνέπεια.
- **Ανάλυση ανά δυσκολία.** Το crossover pattern (raw SQL καλύτερη σε απλά queries, Standardised σε σύνθετα) παρέμεινε στατιστικά μη επιβεβαιωμένο (p = 0.1996 και p = 0.2529). Η ταξινομία σφαλμάτων καλύπτει το ίδιο ερώτημα με μεγαλύτερη ανάλυση.

- `13c_measure_schema_linking_quality.py` — SLR/FPR + ποσοστό διατήρησης
- `13d_evaluate_schema_linked_execution.py` — execution accuracy + McNemar

**Ενοποίηση και ανάλυση:**
- `14_build_master_results.py` — **ενιαίος πίνακας**: μία γραμμή ανά ερώτηση, μία στήλη ανά συνθήκη. Προϋπόθεση για όλα τα επόμενα
- `15_statistical_power.py` — confidence intervals και minimum detectable effect
- `16_decompose_schema_gap.py` — αποσύνθεση της απόστασης Retrieved → Perfect
- `17_retrieval_quality_per_question.py` — retrieval quality ανά ερώτηση
- `18_stratified_memory_analysis.py` — ανάλυση κατά υποομάδες + permutation test
- `19_error_taxonomy.py` — ταξινομία σφαλμάτων και ποσοστά επιδιόρθωσης
- `20_generate_combined.py` — generation με schema linking **και** few-shot μαζί
- `21_factorial_analysis.py` — Cochran's Q, Holm-Bonferroni, interaction test
- `22_worked_example.py` — πλήρες ίχνος του μηχανισμού schema linking σε μία ερώτηση

Κάθε script από το `14` και μετά που ξαναϋπολογίζει παλιότερα μεγέθη περιλαμβάνει **έλεγχο επαλήθευσης** που πρέπει να τα αναπαράγει ακριβώς πριν χρησιμοποιηθούν τα αποτελέσματά του.

`results/` — αποτελέσματα generation (JSON) και οι πίνακες ανάλυσης (CSV).

`technical_document_v2.docx` — αναλυτική τεκμηρίωση όλων των παραπάνω.

## Setup

Τα scripts εξαρτώνται από το [Xander repository](https://github.com/henrijsprincis/Xander) και **τρέχουν μέσα από αυτό**: χρησιμοποιούν τα modules `eval.process_sql` και `open_ai.chat_gpt`, τις SQLite βάσεις του Spider (`database/`), και τα τοπικά `.index` / `.pkl` αρχεία. Εκτέλεση από αυτό εδώ το repository αποτυγχάνει με `ModuleNotFoundError: No module named 'eval'`.

```bash
git clone https://github.com/henrijsprincis/Xander.git
cd Xander
pip install -r requirements.txt
tar -xf database.zip
```

Αντίγραψε τα scripts αυτού του repository μέσα στον φάκελο `Xander/`, εγκατέστησε τα επιπλέον requirements:

```bash
pip install -r requirements.txt
```

και δημιούργησε `.env` μέσα στον `Xander/` με:

```
OPENAI_API_KEY=...
HF_TOKEN=...
```

Τρέξε τα scripts με τη σειρά της Δομής Repository. Τα ενδιάμεσα αρχεία (`.index`, `.pkl`, μεγάλα `sample_*.json`) δεν είναι committed (βλ. `.gitignore`) — αναπαράγονται τρέχοντας τα scripts με τη σειρά.
